# MVP integration research and data provenance

Checked during implementation on 2026-10-17. These findings describe the connected integration, not an assumption of financial-provider eligibility.

## Frankfurter v2 — connected

- Official documentation: https://frankfurter.dev/
- Machine-readable overview: https://frankfurter.dev/llms.txt
- OpenAPI: https://api.frankfurter.dev/v2/openapi.json
- Connected pair endpoint: https://api.frankfurter.dev/v2/rate/CNY/VND
- Connected history endpoint: https://api.frankfurter.dev/v2/rates?from=2026-10-03&base=CNY&quotes=VND (date range is generated by the application).

The official service permits no-key access and local caching of its blended daily reference data. The implementation parses rate JSON numbers directly into Decimal, validates the pair/date/value, and persists observations. It displays attribution and observation/fetch timestamps. A direct upstream call returned HTTP 200 with CNY/VND 3864.07, observation 2026-10-16; the real running-app HTTP smoke also verified this integration. `submission/evidence/mvp-live-http.json` records the measured response. A reference observation is not an executable bank conversion price.

## ExchangeRate-API — evaluated, not connected

Official open-access documentation: https://www.exchangerate-api.com/docs/free . Its no-key feed requires attribution, has rate limits and daily refresh. It was unnecessary once Frankfurter's actual CNY/VND response was verified. No undocumented fallback or silent provider substitution is implemented.

## Payment providers — not connected

payOS documentation: https://payos.vn/docs/ . This describes merchant Napas/VietQR collection and merchant-configured webhooks; it does not establish a supported cross-border Chinese insurance settlement corridor. No local Vietnamese bank collection was substituted for the original insurance problem. The user confirmed they do not have a provider sandbox account. No merchant keys, eligible beneficiary onboarding or verified payment corridor are available in this workspace. The application reports the payment integration as SANDBOX, never settled funds.

## User data

Registered accounts begin empty. Invoice data is entered by its owner and marked USER_ENTERED; it is not claimed to have been verified by a university or insurer. Original synthetic records remain restricted to the optional sandbox account. A policy source is the exact file the owner uploads, with optional user-supplied source URL. The app never fetches arbitrary URLs or uploads private text to a third-party API. Search returns original excerpts and page citations, not generated insurance coverage determinations. No canned fictional policy is served to a registered account by the legacy policy endpoint.

QA accounts, invoice input and uploaded policy text in test evidence are explicitly self-authored test fixtures. Only the upstream/reference FX observation in live smoke evidence is external data. The test fixture language must not be presented as actual insurance terms.
